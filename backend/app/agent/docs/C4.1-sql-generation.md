# Camada 4.1 — Geração de SQL

## Visão geral

A camada **4.1 — Geração de SQL** é responsável por interpretar a pergunta do usuário e transformá-la, quando possível, em uma consulta SQL estruturada e segura para posterior validação pela camada 4.2.

Ela faz parte do fluxo principal do agente do **V-Energy Grid 360**:

```text
Pergunta do usuário
        ↓
1. Input Guardrail
        ↓
2. Cache
        ↓
3. Fallback de IA
        ↓
4. Agente
   ├── 4.1 Geração de SQL
   ├── 4.2 SQL Guardrail
   ├── 4.3 Execução no banco
   └── 4.4 Síntese da resposta
        ↓
5. Output Guardrail
        ↓
6. Pós-processamento
```

A 4.1 **não executa consultas no banco** e também **não substitui o SQL Guardrail**. Seu papel é produzir uma proposta de consulta SQL ou indicar, por meio de um status estruturado, por que uma consulta não deve ou não pode ser produzida.

---

## Objetivos da camada

A camada 4.1 foi construída para:

- interpretar perguntas em linguagem natural;
- identificar se a solicitação pertence ao domínio do V-Energy Grid 360;
- utilizar contexto recente da conversa quando houver continuidade;
- verificar se há informação suficiente para produzir SQL;
- diferenciar ausência de contexto de necessidade de esclarecimento;
- identificar tentativas de manipulação semântica que passaram pelo Input Guardrail;
- gerar uma única consulta SQL de leitura quando possível;
- produzir uma saída estruturada e validável pela aplicação;
- utilizar o mecanismo de fallback de providers já existente no projeto.

---

## Responsabilidades

A camada 4.1 é responsável por:

1. interpretar a intenção da pergunta;
2. considerar o contexto recente da conversa;
3. analisar o schema/contexto do banco recebido;
4. classificar a solicitação em um dos status suportados;
5. gerar SQL quando o status for `READY`;
6. rejeitar manipulações ou solicitações incompatíveis com as regras internas;
7. devolver um objeto estruturado para as próximas etapas do agente.

A camada 4.1 **não é responsável por**:

- executar SQL;
- validar definitivamente a segurança estrutural da consulta;
- consultar o banco;
- confirmar existência real de tabelas ou colunas sem o schema definitivo;
- sintetizar a resposta final ao usuário;
- persistir memória da conversa;
- gerenciar cache;
- expor detalhes internos de segurança ou de providers.

## Arquitetura implementada

### Prompts

Os prompts fixos da camada ficam em:

```text
app/agent/prompts/sql_generation/
├── __init__.py
├── loader.py
├── system.md
├── domain.md
├── security.md
├── sql_rules.md
└── output_contract.md
```

A divisão foi adotada para evitar um único prompt extenso dentro do código Python e permitir manutenção independente das regras.

### Loader

O arquivo:

```text
app/agent/prompts/sql_generation/loader.py
```

carrega os cinco arquivos Markdown nesta ordem:

```text
system.md
    ↓
domain.md
    ↓
security.md
    ↓
sql_rules.md
    ↓
output_contract.md
```

O loader também valida se:

- todos os arquivos existem;
- nenhum arquivo está vazio;
- a ordem esperada é preservada;
- espaços desnecessários nas extremidades são removidos.

### SQL Generator

O arquivo:

```text
app/agent/sql_generator.py
```

é a interface principal da etapa 4.1.

Ele recebe:

```python
question: str
database_context: str
memory_context: str | None
```

e utiliza:

```text
Prompts fixos
    +
Pergunta atual
    +
Memória recente opcional
    +
Contexto/schema do banco
        ↓
run_with_fallback()
        ↓
Gemini / OpenRouter
        ↓
SQLGenerationResult
```

## Separação entre instruções e dados dinâmicos

Os prompts em Markdown representam as **instruções fixas** da etapa.

Já os dados dinâmicos são enviados separadamente:

```text
<user_question>
...
</user_question>

<conversation_context>
...
</conversation_context>

<database_context>
...
</database_context>
```

Essa separação ajuda o modelo a distinguir instruções internas de conteúdos não confiáveis fornecidos pelo usuário, memória ou banco.

## Contrato estruturado de saída

A resposta da 4.1 utiliza o schema:

```python
SQLGenerationResult
```

com os campos:

```text
status
sql
reason
```

Os status suportados são:

### `READY`

Utilizado quando existe informação suficiente para gerar uma consulta SQL.

```text
sql    → obrigatório
reason → null
```

### `OUT_OF_SCOPE`

Utilizado quando a pergunta não pertence ao domínio do V-Energy Grid 360.

```text
sql    → null
reason → obrigatório
```

### `NEEDS_CLARIFICATION`

Utilizado quando falta uma informação objetiva que o usuário consegue fornecer.

Exemplo:

```text
"Quanto o faturamento aumentou?"
```

Sem uma referência de comparação, o agente deve pedir uma informação específica, como o período desejado.

```text
sql    → null
reason → pergunta curta e específica
```

### `INSUFFICIENT_CONTEXT`

Utilizado quando a pergunta pertence ao domínio, porém o contexto disponível não possui dados, estrutura ou relacionamentos suficientes para gerar SQL com segurança.

Exemplo:

```text
"Qual foi o total de perdas técnicas em Recife em 2026?"
```

Se o schema não possuir informação sobre perdas técnicas, a aplicação não deve inventar tabela ou coluna.

```text
sql    → null
reason → impedimento identificado
```

### `REJECTED`

Utilizado quando existe tentativa de manipulação, prompt injection semântico ou solicitação incompatível com as regras de segurança.

```text
sql    → null
reason → justificativa breve
```

Detalhes internos de segurança não devem ser revelados.

---

## Validação do contrato

O schema Pydantic valida a coerência entre os campos.

Quando:

```text
status = READY
```

é obrigatório existir SQL.

Quando:

```text
status != READY
```

o SQL deve ser `null` e deve existir uma justificativa em `reason`.

Isso impede estados inconsistentes como:

```text
READY sem SQL
```

ou:

```text
REJECTED com SQL preenchido
```

## Decisões de arquitetura

### Uma única chamada de IA na etapa 4.1

Foi decidido não criar um classificador separado antes da geração SQL.

A própria chamada da 4.1 é responsável por:

- classificação de domínio;
- interpretação da intenção;
- avaliação semântica de segurança;
- análise de contexto;
- geração de SQL.

Isso evita um fluxo com três chamadas de IA no caminho normal:

```text
classificador LLM
    ↓
gerador SQL LLM
    ↓
síntese LLM
```

O fluxo esperado permanece com geração SQL e síntese como chamadas separadas.

---

## Segurança semântica

O Input Guardrail continua responsável por bloqueios determinísticos simples, como:

- SQL estrutural enviado diretamente pelo usuário;
- URLs;
- padrões conhecidos de prompt injection;
- entrada inválida;
- tamanho máximo.

Algumas manipulações, porém, dependem de interpretação semântica.

Por isso, a etapa 4.1 também pode retornar `REJECTED` ao detectar tentativa de:

- alterar o papel do agente;
- substituir instruções internas;
- remover restrições;
- revelar prompts;
- solicitar operações proibidas;
- tratar memória ou dados como instruções.

Essa proteção não substitui o SQL Guardrail da etapa 4.2.

---

## Complexidade SQL suportada

A complexidade escolhida para o MVP é intermediária.

São suportados:

```text
SELECT
WHERE
JOIN
GROUP BY
HAVING
ORDER BY
LIMIT
aliases
SUM
AVG
COUNT
MIN
MAX
CASE WHEN simples
```

Devem ser evitados:

- CTEs complexas;
- subqueries profundamente aninhadas;
- window functions;
- consultas excessivamente complexas para validação.

Se uma solicitação exigir complexidade além do suporte atual e não existir alternativa segura, a camada pode retornar `INSUFFICIENT_CONTEXT`.

---

## Operações permitidas

A camada 4.1 deve gerar apenas consultas de leitura.

Nunca deve produzir operações como:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
CREATE
TRUNCATE
GRANT
REVOKE
```

Também não deve gerar múltiplas instruções SQL.

Essas regras serão verificadas novamente, de forma determinística, pela etapa **4.2 — SQL Guardrail**.

A arquitetura assume que a saída de uma LLM nunca deve ser considerada confiável apenas porque o prompt contém regras de segurança.

---

## Consultas multidomínio

Consultas envolvendo múltiplos domínios são permitidas quando os relacionamentos necessários estiverem explicitamente disponíveis no schema recebido.

A camada não pode inventar:

- chaves estrangeiras;
- relacionamentos;
- tabelas intermediárias;
- campos;
- regras de associação.

Quando o relacionamento necessário não estiver disponível, a resposta deve ser `INSUFFICIENT_CONTEXT`.

---

## Uso de memória

A função `generate_sql()` já aceita:

```python
memory_context: str | None
```

A memória pode ser usada para resolver perguntas de continuidade.

Exemplo:

```text
Pergunta anterior:
"Qual foi o consumo de Recife em 2026?"

Pergunta atual:
"E Garanhuns?"
```

Com o contexto recente, a 4.1 pode interpretar a pergunta atual como uma continuação da anterior.

A etapa 4.1 **não é responsável por armazenar ou construir a memória**.

A arquitetura prevista é:

```text
Histórico da sessão
        ↓
últimas 5 interações
        ↓
memory_context
        ↓
4.1 — Geração de SQL
```

A persistência dessa memória poderá ser implementada posteriormente no banco definido pelo backend.

## Providers e fallback

A 4.1 não chama diretamente um provider específico.

Ela utiliza:

```python
run_with_fallback()
```

Fluxo atual:

```text
Gemini 3.1 Flash-Lite
        ↓
falha recuperável
        ↓
OpenRouter
        ↓
Nemotron 3 Super
        ↓
Nemotron 3 Ultra
        ↓
Gemma 4 31B
```

Isso mantém a geração SQL desacoplada da infraestrutura de providers.

O Gemini foi testado diretamente nesta etapa.

O fluxo de fallback do OpenRouter já possui testes próprios na camada de providers, mas ainda não foi executado um teste de integração real específico da 4.1 forçando falha do Gemini e geração SQL via OpenRouter.

Essa validação pode ser realizada posteriormente e não bloqueia o desenvolvimento atual.

## Schema mock

Como o schema Gold definitivo ainda não estava disponível durante a implementação da 4.1, foi utilizado um schema mock exclusivamente para testes.

O mock contém estruturas representativas de:

- consumo de energia;
- faturamento;
- interrupções;
- atendimentos;
- relacionamentos conhecidos.

Ele existe apenas para permitir:

- desenvolvimento da geração SQL;
- testes de structured output;
- validação dos status;
- testes reais com Gemini;
- testes de contexto insuficiente.

O mock **não representa o banco definitivo do projeto**.

Ele deve permanecer isolado da lógica de produção e ser utilizado apenas como fixture/contexto de testes.

---

## Mudanças quando o banco Gold estiver disponível

A chegada do banco real não exige reconstrução da camada 4.1.

A arquitetura atual já recebe o schema externamente por meio de:

```python
database_context
```

Quando o banco estiver disponível, será necessário:

1. mapear as tabelas Gold reais;
2. mapear colunas e tipos relevantes;
3. mapear relacionamentos reais;
4. substituir o schema mock utilizado nos testes;
5. validar consultas geradas contra tabelas e colunas reais;
6. ajustar descrições de domínio caso o schema definitivo introduza novos conceitos;
7. executar benchmark Text-to-SQL com perguntas representativas do caso;
8. avaliar se o schema completo deve ser enviado integralmente ou recuperado de forma seletiva;
9. medir o consumo real de tokens;
10. revisar os prompts apenas se os testes com o schema real demonstrarem necessidade.

Não deve ser feito hardcode das tabelas do mock no código de produção.

## Comportamento não determinístico de providers

Durante uma das execuções reais, um teste retornou temporariamente:

```text
ProviderErrorType.UNKNOWN
```

Ao repetir o mesmo cenário, o teste passou corretamente. Em uma execução completa posterior, os cinco testes passaram.

Não houve evidência suficiente para atribuir o problema ao prompt.

O episódio revelou, porém, uma melhoria futura importante para observabilidade.

Quando uma exceção não reconhecida pelo classificador ocorrer, a camada de observabilidade deverá registrar informações como:

- provider;
- modelo;
- número da tentativa;
- classe real da exceção;
- mensagem técnica;
- latência;
- sucesso ou falha;
- tipo de erro classificado.

Esses detalhes devem ficar disponíveis apenas para diagnóstico interno e não devem ser expostos ao usuário final.

O `print` temporário utilizado durante a investigação não deve permanecer como mecanismo definitivo de observabilidade.

## Testes normais versus testes reais

Os testes unitários devem permanecer rápidos, determinísticos e sem custo de API.

Os testes reais de LLM devem ser executados explicitamente.

Durante o desenvolvimento:

```powershell
python -m pytest tests/agent -v
```

Quando for necessário validar a LLM real:

```powershell
$env:RUN_LLM_INTEGRATION="1"
python -m pytest tests/agent/integration/test_sql_generation_gemini.py -v -s
```

Isso evita consumo acidental de requisições.
