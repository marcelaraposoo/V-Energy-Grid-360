# Camada 4.2 — SQL Guardrail

## Visão geral

A camada **4.2 — SQL Guardrail** é responsável por validar, de forma determinística, o SQL produzido pela etapa **4.1 — Geração de SQL** antes que qualquer consulta seja encaminhada para execução.

Seu objetivo principal é impedir que uma saída incorreta, insegura ou incompatível com as regras do agente chegue ao banco de dados.

O SQL Guardrail não utiliza LLM. Toda a validação é realizada por código.

Fluxo simplificado:

```text
4.1 — Geração de SQL
        ↓
SQL candidato
        ↓
4.2 — SQL Guardrail
        ↓
ALLOW ou BLOCK
        ↓
4.3 — Execução no banco
```

A camada funciona como uma barreira de segurança entre a geração probabilística da IA e a execução determinística no banco.

---

## Objetivo da camada

A 4.2 existe para responder a uma pergunta simples:

> A consulta SQL produzida pela IA é estruturalmente segura e compatível com o tipo de consulta permitido pelo agente?

Ela não tenta interpretar a intenção do usuário e não decide se a pergunta pertence ao domínio da aplicação.

Essas responsabilidades pertencem à 4.1.

A função da 4.2 é analisar apenas o SQL recebido.

---

## Responsabilidades

A camada é responsável por:

- validar se o conteúdo recebido pode ser interpretado como SQL;
- permitir apenas consultas de leitura;
- bloquear operações de escrita;
- bloquear comandos que alterem estrutura ou permissões;
- impedir múltiplas instruções SQL na mesma saída;
- bloquear estruturas SQL não suportadas pelo MVP;
- preservar o SQL original recebido;
- indicar se uma reprovação pode gerar uma nova tentativa da 4.1;
- produzir feedback determinístico para uma única regeneração;
- falhar de forma segura caso o próprio guardrail apresente erro interno.

A camada não é responsável por:

- gerar SQL;
- corrigir ou reescrever SQL automaticamente;
- executar consultas;
- consultar o banco;
- limitar quantidade de linhas retornadas;
- formatar resultados;
- sintetizar resposta ao usuário;
- controlar providers de IA;
- decidir qual modelo será utilizado;
- controlar diretamente a regeneração da 4.1.

---

## Princípio de segurança

A arquitetura parte do princípio de que uma saída de LLM nunca deve ser considerada confiável apenas porque o prompt contém regras de segurança.

Mesmo que a 4.1 seja instruída a produzir exclusivamente consultas de leitura, toda consulta gerada precisa passar pela 4.2 antes de qualquer execução.

Exemplo:

```text
Usuário
  ↓
4.1 gera:
DELETE FROM faturamento;
  ↓
4.2 detecta operação proibida
  ↓
BLOCK
```

A consulta nunca chega ao banco.

---

## Parser SQL

A camada utiliza **SQLGlot** para transformar o SQL em uma estrutura sintática analisável.

Dependência utilizada:

```text
sqlglot==30.24.0
```

Dialeto configurado:

```text
sqlite
```

O uso de parser foi escolhido em vez de validação baseada apenas em expressões regulares.

Isso permite distinguir corretamente elementos como:

```sql
SELECT *
FROM atendimentos
WHERE tipo_atendimento = 'DELETE FROM faturamento';
```

Nesse caso, `DELETE FROM faturamento` é apenas conteúdo textual de uma string e não uma operação SQL real.

Da mesma forma:

```sql
SELECT *
FROM consumo_energia
/* DROP TABLE faturamento */;
```

continua sendo uma consulta de leitura válida, porque o `DROP` aparece apenas dentro de um comentário.

---

## Contrato de saída

A camada retorna um `SQLGuardrailResult`.

O resultado possui:

```text
decision
reason
retryable
original_sql
```

### `ALLOW`

Indica que a consulta passou pelas regras estruturais da camada.

```text
decision = ALLOW
reason = null
retryable = false
original_sql = SQL recebido
```

### `BLOCK`

Indica que a consulta não pode seguir para a próxima etapa.

```text
decision = BLOCK
reason = motivo da reprovação
retryable = true ou false
original_sql = SQL recebido
```

---

## Motivos de bloqueio

### `INVALID_SQL`

Usado quando:

- o SQL está vazio;
- o parser não consegue interpretar a consulta;
- o conteúdo não representa uma consulta de leitura reconhecida.

Exemplos:

```text
""
```

```text
THIS IS NOT SQL
```

```sql
SELECT FROM;
```

### `MULTIPLE_STATEMENTS`

Usado quando a saída contém mais de uma instrução SQL.

Exemplo:

```sql
SELECT * FROM consumo_energia;
DELETE FROM faturamento;
```

Mesmo duas consultas de leitura são bloqueadas:

```sql
SELECT * FROM consumo_energia;
SELECT * FROM faturamento;
```

A camada aceita exatamente uma instrução SQL por geração.

### `FORBIDDEN_OPERATION`

Usado quando existe uma operação capaz de alterar dados ou estrutura.

São bloqueadas estruturas como:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
CREATE
TRUNCATE
```

Também são rejeitados comandos que não representam consultas de leitura permitidas.

### `UNSUPPORTED_QUERY`

Usado quando a consulta é válida, porém utiliza uma estrutura que foi deliberadamente excluída do escopo atual.

No MVP, funções de janela são bloqueadas.

Exemplo:

```sql
SELECT
    municipio,
    ROW_NUMBER() OVER (
        PARTITION BY municipio
        ORDER BY consumo_kwh DESC
    ) AS posicao
FROM consumo_energia;
```

### `GUARDRAIL_INTERNAL_ERROR`

Usado quando o problema ocorre dentro da própria camada.

Nesse caso:

```text
decision = BLOCK
retryable = false
```

A política é **fail closed**.

Se a camada de segurança falhar, a consulta não continua.

---

## Consultas permitidas

O escopo atual permite consultas de leitura compatíveis com o nível intermediário definido para o agente.

Exemplos de estruturas permitidas:

```text
SELECT
WHERE
JOIN
GROUP BY
HAVING
ORDER BY
LIMIT
UNION
INTERSECT
EXCEPT
aliases
SUM
AVG
COUNT
MIN
MAX
CASE WHEN simples
```

---

## O Guardrail não reescreve SQL

Uma decisão importante de arquitetura foi manter a 4.2 como um componente de validação, e não como um componente de transformação.

A camada:

```text
recebe SQL
    ↓
analisa
    ↓
ALLOW ou BLOCK
```

Ela não:

- acrescenta `LIMIT`;
- remove comandos;
- troca tabelas;
- corrige sintaxe;
- reescreve a consulta.

Essa decisão evita que uma camada de segurança passe a modificar silenciosamente a intenção original da consulta.

---

## Volume de resultados

A 4.2 não bloqueia consultas apenas porque podem retornar muitas linhas.

Por exemplo:

```sql
SELECT *
FROM consumo_energia;
```

pode ser considerada estruturalmente segura.

Questões como:

- volume retornado;
- timeout de execução;
- quantidade máxima de registros;
- processamento do resultado;
- apresentação ao usuário;

pertencem às etapas posteriores do fluxo.

A responsabilidade da 4.2 permanece restrita à segurança e estrutura do SQL.

---

## Regeneração após bloqueio

Foi decidido permitir **no máximo uma regeneração** quando o SQL produzido pela 4.1 é rejeitado por um motivo corrigível.

Fluxo:

```text
4.1 gera SQL
    ↓
4.2 valida
    ↓
BLOCK + retryable = true
    ↓
feedback de correção
    ↓
4.1 gera novamente
    ↓
4.2 valida novamente
```

Se a segunda consulta também for bloqueada:

```text
encerra o fluxo
```

Não existe terceira tentativa.

Essa decisão limita:

- consumo de tokens;
- latência;
- número de chamadas externas;
- risco de loops;
- tempo de espera do usuário.

---

## Reprovações que permitem regeneração

Atualmente:

```text
INVALID_SQL             → retryable = true
MULTIPLE_STATEMENTS     → retryable = true
FORBIDDEN_OPERATION     → retryable = true
UNSUPPORTED_QUERY       → retryable = true
```

Isso ocorre porque esses problemas podem ter sido gerados pela LLM e podem ser corrigidos em uma segunda geração.

---

## Erros que não permitem regeneração

```text
GUARDRAIL_INTERNAL_ERROR → retryable = false
```

Se a própria camada de segurança falhou, não existe motivo para gastar uma nova chamada de IA tentando corrigir a consulta.

---

## Feedback para a 4.1

Quando uma reprovação é corrigível, a camada consegue produzir feedback determinístico com:

- SQL rejeitado;
- motivo da reprovação;
- instrução para gerar uma nova consulta.

Foi decidido enviar para a 4.1 tanto:

```text
SQL rejeitado
+
motivo da rejeição
```

em vez de apenas informar genericamente que a consulta falhou.

Isso aumenta a chance de a única regeneração disponível corrigir exatamente o problema identificado.

---

## Separação entre Guardrail e Orquestração

Outra decisão importante foi impedir que a própria 4.2 controle o fluxo de retry.

A 4.2 apenas retorna:

```text
ALLOW / BLOCK
reason
retryable
original_sql
```

Quem controla o ciclo é o orquestrador.

Isso mantém responsabilidades separadas:

```text
4.1            → gera SQL
4.2            → valida SQL
Orquestrador   → controla fluxo
Router         → controla providers
```

---
## Orquestrador

O fluxo entre 4.1 e 4.2 é controlado por:

```text
app/agent/sql_generation_orchestrator.py
```

Limite configurado:

```python
MAX_GUARDRAIL_REGENERATIONS = 1
```

O orquestrador:

1. chama a geração SQL;
2. recebe o resultado;
3. envia SQL `READY` para a 4.2;
4. encerra imediatamente em `ALLOW`;
5. verifica `retryable` em caso de `BLOCK`;
6. constrói feedback;
7. permite uma única regeneração;
8. envia o novo SQL novamente ao Guardrail;
9. encerra após a segunda validação, independentemente do resultado.

---

## Casos que não passam pela 4.2

Se a 4.1 retornar um status sem SQL, o Guardrail não é chamado.

Exemplos:

```text
OUT_OF_SCOPE
NEEDS_CLARIFICATION
INSUFFICIENT_CONTEXT
REJECTED
```

Isso ocorre porque não existe SQL para validar.

## Testes implementados

A camada recebeu testes unitários específicos e uma bateria adversarial.

### Testes básicos

Foram testados:

- `SELECT` simples;
- agregações;
- `JOIN`;
- `CASE WHEN`;
- `WHERE`;
- `GROUP BY`;
- `HAVING`;
- `ORDER BY`;
- `LIMIT`;
- `INSERT`;
- `UPDATE`;
- `DELETE`;
- `DROP`;
- `ALTER`;
- `CREATE`;
- `TRUNCATE`;
- SQL vazio;
- SQL inválido;
- múltiplas statements;
- funções de janela;
- preservação do SQL original;
- falha interna do Guardrail.

### Testes adversariais

Foram testados casos como:

- palavra `DELETE` dentro de string;
- palavra `DROP` dentro de comentário;
- ponto e vírgula dentro de string;
- `SELECT` seguido de operação destrutiva;
- duas consultas de leitura separadas;
- comandos administrativos como `PRAGMA`, `VACUUM`, `ATTACH DATABASE`, `DETACH DATABASE`, `BEGIN`, `COMMIT` e `ROLLBACK`.

Esses testes ajudam a comprovar que a validação estrutural por AST evita falsos positivos e bypasses simples que seriam comuns em uma abordagem baseada apenas em regex.

---

## Testes do feedback de regeneração

Foram criados testes específicos para garantir que o feedback:

- só seja produzido em `BLOCK`;
- só seja produzido quando `retryable = true`;
- contenha o SQL rejeitado;
- contenha o motivo;
- solicite nova geração;
- não seja produzido em `ALLOW`;
- não seja produzido em erro interno do Guardrail.

---

## Testes do orquestrador

O fluxo integrado entre 4.1 e 4.2 também foi testado.

Foram cobertos:

- aprovação na primeira tentativa;
- bloqueio seguido de correção;
- bloqueio nas duas gerações;
- resultado da 4.1 sem SQL;
- erro de provider;
- limite de uma única regeneração.

---

## Resultado dos testes

A suíte da camada passou integralmente.

Após a implementação do Guardrail, feedback e orquestrador, também foi executada a suíte completa do agente para garantir que a nova camada não introduziu regressões nas etapas anteriores.

Todos os testes passaram.

## Conclusão

A camada **4.2 — SQL Guardrail** cria uma barreira determinística entre a geração probabilística de SQL e a execução no banco.

Sua principal função é garantir que apenas consultas SQL de leitura, estruturalmente válidas e compatíveis com as regras do agente possam seguir no fluxo.

A camada foi projetada com responsabilidades bem delimitadas:

```text
4.1 → gera
4.2 → valida
Orquestrador → controla retry
Router → controla providers
4.3 → executa
```

Com isso, uma falha da LLM não implica automaticamente risco para o banco.

Mesmo quando uma consulta é bloqueada, o sistema permite apenas uma correção controlada antes de encerrar o fluxo, mantendo equilíbrio entre segurança, custo e latência.
