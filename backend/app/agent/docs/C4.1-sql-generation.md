# Camada 4.1 — Geração de SQL

## 1. Visão geral

A camada **4.1 — Geração de SQL** interpreta perguntas em linguagem natural e, quando possível, produz uma consulta SQL estruturada para validação pela camada **4.2 — SQL Guardrail**.

Fluxo:

```text
Pergunta do usuário
        ↓
Input Guardrail
        ↓
Fallback de IA
        ↓
4.1 — Geração de SQL
        ↓
4.2 — SQL Guardrail
        ↓
4.3 — Execução no banco
        ↓
4.4 — Síntese
```

A 4.1 não executa SQL e não substitui a validação determinística da 4.2.

---

## 2. Responsabilidades

A camada é responsável por:

- interpretar a intenção do usuário;
- compreender termos do domínio V-Energy;
- utilizar contexto recente da conversa;
- analisar o contexto Gold recebido;
- classificar a solicitação;
- gerar SQL quando possível;
- rejeitar manipulações semânticas;
- receber feedback da 4.2 para uma única regeneração.

Não é responsabilidade da 4.1:

- executar consultas;
- persistir memória;
- gerenciar cache;
- validar definitivamente a segurança estrutural do SQL;
- sintetizar a resposta final.

## 3. Arquitetura

Os prompts ficam em:

```text
app/agent/prompts/sql_generation/
├── system.md
├── domain.md
├── security.md
├── sql_rules.md
├── output_contract.md
└── loader.py
```

O loader mantém a ordem:

```text
system
→ domain
→ security
→ sql_rules
→ output_contract
```

A interface principal é:

```text
app/agent/sql_generator.py
```

A função recebe:

```python
question
database_context
memory_context
guardrail_feedback
```

e utiliza o router de providers para obter um `SQLGenerationResult`.

---

## 4. Contrato de saída

A saída possui:

```text
status
sql
reason
```

Status suportados:

### `READY`

Existe informação suficiente para gerar SQL.

```text
sql    → obrigatório
reason → null
```

### `OUT_OF_SCOPE`

A pergunta não pertence ao domínio V-Energy.

### `NEEDS_CLARIFICATION`

Falta uma informação objetiva que o usuário consegue fornecer.

### `INSUFFICIENT_CONTEXT`

A pergunta pertence ao domínio, mas o contrato de dados não possui informação suficiente para respondê-la com segurança.

### `REJECTED`

A solicitação contém manipulação semântica, prompt injection ou intenção incompatível com as regras internas.

Para qualquer status diferente de `READY`:

```text
sql    → null
reason → obrigatório
```

## 6. Regras SQL

A 4.1 trabalha apenas com consultas de leitura.

Suportado no MVP:

```text
SELECT
WHERE
JOIN
GROUP BY
HAVING
ORDER BY
LIMIT
aliases
SUM
AVG
COUNT
MIN
MAX
CASE WHEN simples
```

Devem ser evitados:

- CTEs complexas;
- subqueries profundamente aninhadas;
- window functions;
- múltiplas instruções.

Operações de escrita não devem ser geradas:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
CREATE
TRUNCATE
```

A validação definitiva ocorre na 4.2.

## 7. Integração com a 4.2

A camada **4.2 — SQL Guardrail** já está implementada.

Fluxo:

```text
4.1 gera SQL
        ↓
4.2 valida
        ↓
ALLOW
        ↓
continua
```

Quando a 4.2 bloqueia um SQL por motivo recuperável:

```text
BLOCK
  ↓
feedback determinístico
  ↓
uma regeneração na 4.1
  ↓
nova validação
```

O limite é de **uma única regeneração**, evitando loops.

## 8. Providers

A 4.1 não depende diretamente de um provider específico.

Ela utiliza:

```python
run_with_fallback()
```

Pool atual:

```text
Gemini 3.1 Flash-Lite
        ↓
Gemma 4 31B
        ↓
Nemotron 3 Ultra
```

A lógica de fallback pertence à Camada 3.

Erros de provider são convertidos para `ProviderErrorType` e propagados de forma controlada.

Também existe:

```text
app/agent/provider_responses.py
```

para transformar erros internos em mensagens seguras para o usuário.

A disponibilidade real dos providers pode variar. O Nemotron Ultra permanece sob observação devido a ocorrências de `INVALID_OUTPUT`.
